Using more effectively5 entries

It works. I'm learning to use it better.

  1. The problem before the prompt

    13 October 2026 · Draft

    Give a coding agent a feature request and it builds the feature. Give it the problem and who has it, and its output has something to be checked against. Without that, it fills the gap with plausible features. Naming the problem is the cheapest fix for agent output I know.

    • In the field guide: Problem-Based Software Requirements Specification · 2016
    • 1On the route: Purpose · Is this worth building, and what would prove it?

  2. Workflows before autonomous agents

    13 October 2026 · Draft

    Most tasks I'd hand to an agent work better as a fixed workflow with one or two model calls. I reach for an open-ended agent loop only when the steps can't be known in advance, and then with a budget on calls.

    • 2On the radar: Workflows before autonomous agents · Adopt
    • In the field guide: Building effective agents · 2024

  3. A baseline before the model

    13 October 2026 · Draft

    Before any model work I want a simple baseline on real data: a rule, a lookup, a heuristic. If the model can't beat it, we stop early. If it can, we know by how much, and the failures get written down, not only the average.

    • 1On the radar: Baseline before model · Adopt
    • In the field guide: Rules of Machine Learning · living
    • 2On the route: Design · Does it work on real data, measured honestly?

  4. Cost per completed task, not per call

    13 October 2026 · Draft

    I look at cost and at the number of model and tool calls per completed task. An agent that retries its way to an answer looks cheap per call and expensive per task. The GenAI conventions carry the token counts to do this per agent.

    • 25On the radar: Cost and calls per completed task · Trial
    • GN-0001 Agentic observability, original note
    • In the field guide: FinOps for AI Overview · living

  5. Small branches and checks that run in seconds

    13 October 2026 · Draft

    Coding agents produce more change than anyone can review carefully in one sitting. So keep their work on short branches, one concern each, behind checks that run in seconds. On this site that is a zero-dependency build and a link checker that refuses broken anchors.

Watch out for7 entries

I'd stop these before production. Each one is on Hold on the radar.

  1. Telemetry that lives only in a vendor's console

    13 October 2026 · Draft

    If the only place to see what your agents did is one vendor's dashboard, you can't join it to the rest of your traces, and you can't leave. Put it in the contract: open conventions, exported to a backend you control.

    • 17On the radar: Telemetry only in a vendor's console · Hold
    • GN-0001 Agentic observability, original note

  2. LLM judges nobody calibrated

    13 October 2026 · Draft

    A model grading another model's output is cheap and fast, and it can be wrong in ways that look confident. Before a judge gates anything, check it against people grading the same samples, and check again when prompts or models change.

    • 27On the radar: LLM judges without human calibration · Hold
    • In the field guide: Who Validates the Validators? · 2024

  3. Benchmark scores as launch evidence

    13 October 2026 · Draft

    A leaderboard result says a model did well on someone else's tasks, once. It says little about your data, your tools or repeated runs. Launch on results from your own tasks, run several times, with the failures written down.

    • 28On the radar: Benchmark scores as launch evidence · Hold
    • In the field guide: AI Agents That Matter · 2024

  4. Retries with no budget

    13 October 2026 · Draft

    Automatic retries feel like resilience until a slow dependency turns every request into several, and the overload spreads. Retries need a budget, backoff and a stop, enforced by the platform rather than left to each agent.

    • 10On the radar: Unbudgeted automatic retries · Hold
    • In the field guide: Addressing Cascading Failures · 2016

  5. Capturing prompts and outputs by default

    13 October 2026 · Draft

    Prompts, outputs and tool arguments often carry personal data. Capturing them makes debugging easier and turns your telemetry into a sensitive data store. Keep capture off unless a written policy turns it on for a named environment, with an owner and a retention period.

    • 40On the radar: Capturing prompts and outputs by default · Hold
    • GN-0001 Agentic observability, original note

  6. A person approving every step as the only safeguard

    13 October 2026 · Draft

    Approval prompts feel safe, but people stop reading them long before the agent stops asking. Keep approval for the decisions that need judgement, and enforce the rest with permissions, limits and checks outside the model.

    • 38On the radar: Human approval as the only safeguard · Hold
    • In the field guide: Ironies of automation · 1983

  7. Blaming the model

    13 October 2026 · Draft

    When an agent gets it wrong, "the model did it" is not an answer. A Canadian tribunal held an airline responsible for what its chatbot told a customer. Whoever deploys the system owns what it says and does, so name that owner before launch.

    • 39On the radar: Shifting accountability to the model or provider · Hold
    • In the field guide: Moffatt v. Air Canada, 2024 BCCRT 149 · 2024
